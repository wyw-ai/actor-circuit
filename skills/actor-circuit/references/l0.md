## Scope and provenance

L0 defines stable, business-independent collaboration-state transitions over Actors. It does not define Actor itself; it imports the [Actor foundation](actor.md).

The underlying structures are not original to this project. Sequence, branching, parallel split, synchronization, partial joins, races, cancellation, loops, and termination have long histories in workflow and distributed-systems research. Cross-participant distinctions also draw from service-interaction research and contemporary Agent frameworks.

This project reorganizes those ideas around a shared Actor foundation, informed by Multi-Actor engineering practice, and separates them from L1 communication and L2 system composition.

Primary antecedents include:

- [Workflow Patterns](https://research.tue.nl/en/publications/workflow-patterns-2/), van der Aalst et al., 2003.
- [Workflow Control-Flow Patterns](https://www.workflowpatterns.com/patterns/control/), Workflow Patterns Initiative.
- [Service Interaction Patterns](https://kodu.ut.ee/~dumas/ServiceInteractionPatterns/documentation.html), Barros, Dumas, and ter Hofstede, 2005.

## Formal core

L0 has three core concepts.

### Collaboration State

Let `C(t)` denote the collaboration state visible at time `t`.

L0 identifies the collaboration facts that must remain distinguishable. It does not prescribe where they live. A runtime may represent them in memory, a database, a filesystem, a message system, an artifact graph, or Human understanding. A durability contract determines which facts survive time and failure.

#### State Element

A State Element is a named projection of `C(t)` whose value must remain observable to one or more later transitions.

Typical State Elements include:

| State Element | Captures |
| --- | --- |
| **Continuation State** | Where execution continues after the current boundary resolves |
| **Ownership State** | Which Actor currently owns execution or continuation |
| **Join State** | Which branches are expected and which have completed |
| **Wait State** | Which condition or event the circuit is waiting for |
| **Round State** | The current loop, review, or retry round |
| **Deadline State** | When a timeout condition becomes observable |

Gates read or change State Elements. In the sequential-circuit analogy, a State Element plays a role similar to a register or latch. The term describes what the circuit remembers; it does not select a storage technology or durability guarantee.

### Gate

A gate is a class of collaboration-state transition triggered by an observable event, fact, or outcome:

```text
g: (C(t), e(t)) → C(t+1)
```

It has an observable enabling condition and produces an observable successor state or terminal state. `e(t)` may be omitted when the triggering fact is already represented in `C(t)`.

### Circuit

A circuit connects gates, State Elements, and their possible continuations:

```text
W = (G, R, E)
```

- `G` is a set of gate instances.
- `R` is a set of State Elements read or changed by those gates.
- `E` relates gate outcomes and state dependencies to successor gates or terminal states.

This graph is not sufficient by topology alone. Gate conditions, branch membership, responsibility changes, waiting, convergence, repetition, and termination must retain their semantics.

## State projections

Gate semantics are derived from what they change in `C(t)`. L0 observes three principal projections rather than promoting every useful noun to a core concept.

### Flow

Flow describes which paths exist, which are enabled or active, and which successor paths may continue.

Branch is a flow state created or selected by a gate, not a peer of Gate in the core model.

### Responsibility

Responsibility describes how Actors relate to a path.

At minimum, distinguish:

- **execution owner** — performs the current bounded work;
- **continuation owner** — holds the right and obligation to advance the next transition.

Observation and visibility must not be inferred from either relationship; they depend on L1 permissions and higher-level policy.

### Lifecycle

Lifecycle distinguishes active, waiting, resumable, and terminal collaboration states.

Silence is not a lifecycle state. A system must not infer success, failure, or waiting merely from lack of activity.

The payload or business meaning of the work is deliberately outside the L0 core. L0 may observe facts or outcomes needed by a gate without defining the domain object being processed.

## Admission criteria

Treat an operation as an L0 gate when it is:

1. **Business-independent** — its semantics survive changes in domain vocabulary.
2. **Semantically stable** — it clearly changes Flow, Responsibility, Lifecycle, or more than one of them.
3. **Composable** — it can participate in a larger circuit rather than naming a complete product or team.
4. **Observable at the boundary** — its enablement and resulting state can be distinguished.

Irreducibility is not required. L0 is a practical engineering vocabulary, not a minimal machine instruction set. However, decomposable policies and multi-gate structures must not be presented as peers of base gates without qualification.

## Base gates

“Base” means first-class named transitions in this working vocabulary, not mathematically irreducible operations.

### Flow gates

#### Sequence

Enable a successor only after its predecessor reaches the required completion state.

```text
complete(A) enables B
```

Dispatching A does not imply completion of A. Sequence defines ordering, not which Actor executes either step or how information is transported.

```text
Understand request → Change code → Run tests
```

#### Branch

Select one or more successor paths from the current collaboration state.

The deciding fact may come from a rule, Human, Agent, or External System. Branch defines the effect on possible continuations, not how the decision is computed.

```text
Tests passed?
  ├─ Yes → Release
  └─ No  → Revise
```

#### Fan-out

Expand one path into multiple independently advancing branches.

```text
1 path → N branches
```

The branches may partition a problem, replicate the same problem, or diversify models, tools, roles, or strategies. Fan-out permits independent progress; it neither requires simultaneous execution nor implies Broadcast.

```text
Research question
  ├─ Agent A → Find evidence
  ├─ Agent B → Find cases
  └─ Agent C → Find counterexamples
```

#### Fan-in

Use the states of multiple branches to enable one successor after a declared convergence condition is satisfied.

```text
N branches → 1 continuation
```

Fan-in defines **when and from which branches** the circuit converges. Aggregation, reduction, voting, selection, and synthesis define **how branch content is processed**.

Its semantics include the relevant branch set, convergence condition, dynamic-membership rule, reset behavior, late-result policy, and fate of remaining branches where applicable.

```text
Evidence ───────┐
Cases ──────────┼→ All required branches complete → Review
Counterexamples ┘
```

### Responsibility gates

#### Route

Select an Actor as a candidate receiver or successor according to capability, content, state, policy, or availability.

Route chooses an Actor. It does not guarantee discovery, delivery, acceptance, execution ownership, or continuation transfer.

```text
Incoming issue
  ├─ Billing question → Billing Actor
  ├─ Technical issue  → Support Actor
  └─ High risk        → Human
```

#### Call

Ask another Actor to perform work while retaining the caller's continuation.

```text
A → B → A
```

The callee may contain an arbitrarily complex internal circuit. At the outer boundary, completion is expected to return to the caller's existing continuation.

```text
Lead → Call Search Actor → Evidence → Lead continues
```

#### Delegate

Assign bounded work to another Actor, changing its execution owner and establishing an expected delivery boundary.

Delegate does not by itself decide final accountability, redelegation, permissions, or budget propagation.

```text
Lead ── Delegate "own the test plan" ──→ QA Actor
```

#### Transfer

Move continuation ownership for a path to another Actor.

```text
A → B → …
```

After Transfer, the previous Actor is no longer a required continuation point. A complete Handoff normally adds L1 context carriage and acceptance. A durable execution environment must also preserve and recover pending transfer state when the system promises continuity across failure.

```text
Frontline Support ── Transfer ──→ Specialist → Resolution
```

#### Return

Resolve a pre-existing Call or Delegate boundary by producing an observable outcome at its declared continuation point.

Outcomes may include completed, partially completed, failed, rejected, or blocked. Ceasing output is not Return.

```text
Worker → Return(completed | failed | blocked) → Lead
```

### Lifecycle gates

#### Wait

Move an active path into a waiting state until a declared condition or event becomes observable.

Wait preserves a future continuation. It is neither failure nor termination.

```text
Submit change → Wait(Human approval) …
```

#### Resume

Move a waiting, suspended, or interrupted path back into an active state when a declared trigger occurs.

Resume restores collaboration state, not necessarily the original process, machine, model session, or Actor instance.

```text
Approval arrives → Resume → Deploy
```

#### Stop

End a collaboration scope with an explicit terminal status, such as succeeded, failed, cancelled, rejected, or exhausted.

No visible activity is not Stop.

```text
Review passed    → Stop(succeeded)
Budget exhausted → Stop(exhausted)
```

## Configured and derived operators

These names remain useful in L0, but they are not presented at the same structural level as the base gates.

### Convergence policies over Fan-in

#### Race

Continue from the first branch satisfying an acceptance condition. Race adds winner selection and must define the fate of non-winning and near-simultaneous branches.

```text
Candidate A ─┐
Candidate B ─┼→ First candidate that passes tests
Candidate C ─┘
```

#### Quorum

Continue after a declared number or weight of eligible branch conditions has been satisfied. Quorum adds threshold, membership, and remaining-branch semantics.

```text
5 reviewers → 3 approvals → Continue
```

`All`, `First`, `Quorum`, and `Best available at a boundary` are examples of Fan-in convergence policies. They do not define result aggregation.

### Resolution around Wait

#### Timeout

Produce an observable outcome when a declared temporal boundary is crossed while a path is waiting or executing.

Timeout is a fact consumed by subsequent circuit logic, commonly Branch. It is not inherently failure and may lead to cancellation, degradation, Retry, Route, Human intervention, or Stop.

```text
Wait for approval
  ├─ Approval arrives → Resume
  └─ 24 hours pass    → Timeout → Escalate
```

### Repetition circuits

#### Loop

Create a back edge from a declared outcome to an earlier circuit region until a termination condition holds.

Loop is a circuit form built from gates and continuations. It requires an observable condition and a bound on rounds, time, cost, or another resource.

```text
Draft → Review → Good enough?
  ↑                 │
  └──── No ─────────┘
```

#### Retry

Repeat a declared operation after selected outcomes and within an attempt or resource budget.

Retry is a failure-conditioned Loop with additional side-effect and idempotency concerns. Its semantics include the target operation, retryable outcomes, limit, delay or backoff, and treatment of earlier effects.

```text
Call API → Temporarily unavailable → Retry within budget
```

## Essential distinctions

| Do not conflate | Distinction |
| --- | --- |
| Fan-out / Broadcast | Fan-out creates work paths; Broadcast changes information visibility. |
| Fan-in / Reduce | Fan-in controls convergence; Reduce processes content. |
| Branch / Route | Branch selects successor paths; Route selects an Actor. |
| Route / Transfer | Route selects a candidate destination; Transfer changes continuation ownership. |
| Call / Delegate | Call preserves a caller continuation; Delegate changes execution ownership. |
| Delegate / Transfer | Delegate changes the executor; Transfer changes the continuation owner. |
| Wait / Stop | Wait preserves a future continuation; Stop creates a terminal state. |
| Race / Voting | Race is a convergence policy; Voting is a possible decision mechanism. |
| Gate / Circuit | A gate is one stable transition; a circuit connects gates, State Elements, and continuations. |
| Circuit / Pattern | A circuit describes state transitions; a pattern resolves recurring forces and includes consequences. |

## Semantic completeness

A circuit need not answer every engineering question, but it must not hide a question that changes its collaboration semantics.

Relevant conditions include:

- **Observable progress:** dispatch, enablement, completion, waiting, and silence are distinguishable where relevant.
- **Explicit state:** later transitions can identify the continuation, ownership, branch, wait, round, or transfer facts they depend on.
- **Explicit continuation:** the next path or continuation owner is knowable after each transition.
- **Responsibility separation:** execution ownership and continuation ownership remain distinguishable.
- **Branch fate:** every Fan-out branch can converge, be cancelled, remain independent, or terminate under an understandable rule.
- **Convergence:** Fan-in policies expose membership, thresholds, late results, and remaining-branch behavior where relevant.
- **Bounded suspension:** Wait exposes what may Resume, time out, cancel, or otherwise resolve it.
- **Bounded repetition:** Loop and Retry expose termination and resource bounds.
- **Explicit transfer:** Transfer identifies the new continuation owner; reliable acceptance belongs to L1.
- **Explicit termination:** Stop produces a terminal fact rather than relying on inactivity.

These are semantic conditions, not a mandatory analysis checklist or output schema. Apply them where they materially affect the circuit.

## What L0 does not define

L0 does not define:

- Actor identifiers, discovery, addressing, or routing tables;
- message or artifact formats;
- delivery, acknowledgement, ordering, duplication, or idempotency mechanisms;
- correlation and causation representation;
- durable storage, offline behavior, resumption transport, or recovery;
- permissions, trust, budgets, or delegation policy;
- result aggregation algorithms;
- complete Multi-Agent system compositions;
- collaboration design patterns and their consequences.

Those concerns motivate L1, the durable execution plane, and L2. L0 may expose them as dependencies without pretending to specify them.
